- **Phase 2D — Admin IAM module (users + roles + RLS-scoping grants).** Second registered module, admin-gated. Manages the three IAM tables (`users`, `roles`, `user_roles`) the rest of the system reads from at login. Granting a role in `user_roles` — optionally scoped to a facility — *is* the runtime RLS knob: `app_current_roles()` and `app_current_facility_id()` are computed from these rows when the JWT is minted. The module deliberately does **not** edit RLS policies themselves; those live in SQL migrations.
- New backend resource at `packages/backend/src/resources/iam/{views,queries,routes,index.ts}`. The three IAM tables share one folder rather than splitting into three near-empty resource folders — they're a single admin domain consumed by a single admin module. Documented deviation from the "one folder per resource" runbook guideline. Endpoints:
  - `GET /users` (list, admin) — paginated, never returns `password_hash` / MFA secret.
  - `POST /users` (admin) — argon2id-hashes the password outside the transaction; rejects duplicate emails with a polite 409 before the UNIQUE constraint trips at 500-cost.
  - `GET /roles` (admin) — alphabetical.
  - `POST /roles` (admin) — name `^[a-z0-9_-]+$` validated.
  - `GET /user-roles?userId=…` (admin) — JOIN'd summary with `roleName` + `facilityName` so the UI renders without re-fetching.
  - `POST /user-roles` (admin) — composite-PK conflict translated from PG `23505` to 409.
- All five endpoints wrap in `withRlsContext` + `writeAudit` + `projectView`; existing RLS policies on `users` / `roles` / `user_roles` from migration 0003 gate at the row level on top of the app-layer `requirePermission`. No schema or policy changes needed.
- New `Permissions.User.{Read,Write}` and `Permissions.Role.{Read,Write}` — granted only to the `admin` role. Granting/revoking user→role assignments is gated by `User.Write` (changing a user's role set is a user-management operation, not a separate permission).
